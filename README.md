# Dream League

*(Mini Strategy Roper League — internally still referred to by the older "WA Mini League" name in a few places: the repo folder, the D1 database name, `package.json`. Renaming those touches live infrastructure identifiers, so they're left alone unless you want that changed too.)*

A tiny 4-page site for tracking a Worms Armageddon mini-league from `.WAgame` replays:

- **`/`** — drop a replay, confirm/map the detected player names, submit. The winner is verified automatically — nothing to pick, unless auto-verification fails, in which case you're prompted to pick the winner yourself so the game still gets recorded. Results go live immediately. Below the drop zone: the league's scheme (`Strategy Roper`) and map pack, both downloadable, plus a link to the full scheme explainer.
- **`/scheme.html`** — what SRoper is, how it differs from standard Roper, map recommendations, strategy tips, and a self-hosted video walkthrough. Linked from the homepage's Scheme & Maps card; not in the main nav, since it's reference material rather than a task.
- **`/standings.html`** — the ladder, plus a log of every submitted game with a replay download link and a provenance note (WADB-verified, self-reported, or set by an admin). Two independent prizes live here — see below. If you're logged in as an admin (in this browser tab), expanding a game also shows a Delete button here — no need to jump to `/admin.html` just to remove a bad submission.
- **`/admin.html`** — password-gated panel to fix a winner, resolve a game the auto-verification couldn't determine, delete a bad submission, merge/delete duplicate player records, review submitted issue reports, or re-run WADB verification on a stored replay. Every result change is logged with who changed it and when — see the audit trail note below. Logging in here is also what makes the "Admin" tab appear in the nav bar on every page in this browser tab — see below.

Every page also has a **Report an issue** button in the header — anyone can flag a disputed result, bad behaviour, or a site bug without logging in; only admins can see the list.

Runs entirely on Cloudflare Pages: static frontend + Pages Functions for the API, D1 (SQLite) for data, R2 for storing both the uploaded replay files and (separately) public site media like the scheme's video walkthrough.

## How it works

- The `.WAgame` parser (`public/js/parser.js`) runs **client-side** for the player-mapping preview — nothing is uploaded just from picking a file. It's a trimmed port of the dreamwa.re Replay Reader tool: same team/machine-attribution logic, minus the flag/grave image extraction and chat log (not needed here).
- **Team/machine attribution is deliberately conservative, never a guess.** Two attribution strategies exist and both have a real replay proving them wrong on their own: treating a team's `slot` byte as a direct index into the connected-machines list breaks once slot numbers go non-contiguous (a real player's team stored as slot=3 with only 3 machines ever connected); the original dreamwa.re approach this was ported from — pairing teams (sorted by slot) against every machine flagged "has a team" (a byte-signature scan), rank for rank — breaks when that signature false-positives on a genuine spectator, which silently shifts every team ranked after it onto the wrong machine (confirmed: it's exactly what credited a spectator as the opponent in a real submitted replay). The parser now tries the direct link first, and only resolves anything left over by elimination when it's completely unambiguous (exactly one team and one hasTeam-flagged machine left unclaimed); anything less certain is left unresolved (`identityUncertain: true`) rather than guessed either way. The submission UI (`public/index.html`) skips fuzzy-matching for those rows entirely (the fallback name is just the team's own name, not a player handle) and prompts the submitter to pick or type the correct player instead of silently trusting a wrong autofill. WADB is still consulted only for the winning *colour*, never player/team identity — this parser is the sole source of truth for who's who.
- **Winner detection**: a `.WAgame` file doesn't record the outcome itself — WA doesn't store one. On submit, the backend (`functions/api/submit.js`) forwards the replay server-to-server to the [Worms Database API](https://wormsarmageddon.com/developers) (`wormsarmageddon.com`)'s `analyzeReplay` mutation, which actually runs the game engine and returns a real result (`teams[].won` / `winningAllianceColor`), not a guess. That gets matched against the submitted players by team colour to set the winner automatically. `analyzeReplay` is public/unauthenticated and ephemeral — it doesn't store the replay or create a public WADB page, which is exactly why we use it instead of `submitReplay` (that one requires a Discord session per-request, which doesn't work for an unattended server-to-server call; `analyzeReplay` was added by WADB's developer specifically to support this kind of use case). We already keep our own copy of the replay in R2 regardless, so losing WADB-side storage costs us nothing — we just lose the "verified via WADB ↗" link being clickable (games verified this way show the label as plain text instead, since there's no page to link to). If WADB can't determine a result (aborted game, alliance mode, an unreachable/erroring API) the game still saves, just marked `outcome_status = 'unresolved'` — it's excluded from standings until an admin resolves it via the admin panel, so a stuck game never silently skews anyone's record.
- **Diagnosing unresolved games**: every unresolved game also gets an `outcome_note` — the specific reason it couldn't be auto-verified (WADB unreachable, a non-2xx/GraphQL error from WADB, the match reported incomplete, multiple winning teams from alliance mode, or a winning colour that didn't match any submitted player). It's computed in `functions/api/submit.js` (`resolveOutcome()` / `callWadb()`), shown under the game in the admin panel's "Needs review" games, and included as a field in the Discord notification for that submission.
- Player identity across renames (e.g. `dt-Deano` / `Deano` / `dt-Daeno`) is handled by `public/js/similarity.js`: it suggests the most likely existing player (weighted toward the "core" name segment, ignoring clan-tag prefixes/suffixes) but always lets the submitter override or create a new player. Every confirmed raw name gets saved as an alias, so matching gets better over time.
- Submissions apply immediately — no approval queue. Duplicate uploads are blocked by hashing the replay file (SHA-256) and rejecting a second submission of the same hash.
- The admin panel is gated by a single shared password (`ADMIN_PASSWORD` secret), used for editing a winner/draw, resolving an unreviewed game, deleting a submission, and merging/deleting player records. Any manual edit is tagged `winner_source = 'manual'` so it's clear on the game log that it wasn't WADB-verified.
- Player identity cleanup: the fuzzy matcher on submit is a suggestion, not a guarantee, so duplicates can slip in (e.g. "Stoned-Worm" vs "StonedWorm" both getting created because neither matched confidently). The admin panel's Players section fixes this after the fact — **Merge** reassigns every game, win, and alias from one player onto another and deletes the duplicate; **Delete** removes a player outright, but only once they have zero games attached (merge first if they don't).
- Text with special/Latin-1 characters (team names, certain player names, and any UI copy with an em dash) is rendered in JetBrains Mono via the `.name-raw` class rather than the DOS bitmap font, since Perfect DOS VGA 437 mis-renders a number of those codepoints — and it does so *silently*, substituting a different wrong-looking glyph rather than an obvious "missing character" box, which is why several of these went unnoticed for a while (`&middot;` rendering as a stray `¶`/`‖`-ish mark across admin.html and elsewhere, `&laquo;`/`&raquo;` on the admin pager rendering as fraction-looking glyphs). Current policy: any element that always carries a special character defaults to JetBrains Mono at the CSS level rather than relying on each call site to remember (`.err`/`.ok`/`.dl-link`/`.victory-icon`); anywhere a plain ASCII alternative reads just as well (`&middot;` → `|`, `&laquo;`/`&raquo;` → `&lt;`/`&gt;`, `&rarr;` → `->` , `&times;` → `x`), that's used instead so there's nothing to get wrong. Text inside a native `title="..."` tooltip is always safe regardless, since browsers render those with the OS UI font, not the page's CSS.
- **Issue reports**: the "Report an issue" button (`public/js/report.js`, wired up on every page via `<button id="reportBtn">` in the header) opens a small form — category, message, and an optional name/handle if the reporter wants to identify themselves. It posts to `POST /api/reports`, which is public and requires no login, but captures the submitter's IP (`CF-Connecting-IP`) server-side and caps it at 5 reports per IP per hour to prevent spam. Reports are never shown anywhere public — only the admin panel's Reports section (`GET/PATCH/DELETE /api/admin/reports`) can see or act on them, where they can be marked resolved/reopened or deleted. Open reports are always listed first.
- **Discord notifications**: `functions/_discord.js` posts to a Discord webhook whenever a game is submitted (`functions/api/submit.js`) or a report is filed (`functions/api/reports.js`) — games and reports go to separate channels/webhooks, and a report also @-mentions an admin role so it doesn't get missed. Both calls are wrapped in `context.waitUntil(...)`, so the notification fires in the background after the response is already sent — a slow or down Discord webhook never delays or breaks a submission. If a webhook secret isn't set, that notification is just silently skipped. See the Discord setup step below.
- **Manual winner fallback**: if `analyzeReplay` can't determine a result on first submit, `functions/api/submit.js` returns `needsManualWinner: true` without saving anything. The submit page (`public/index.html`) then shows a picker so the submitter can choose the winner (or draw) themselves and resubmit — that second attempt is what actually saves the game, tagged `winner_source = 'submitter'`. This is distinct from `'wadb'` (auto-verified) and `'manual'` (an admin corrected it afterwards), and each is surfaced differently: the submit page shows "(self-reported, not WADB-verified)", the admin panel shows a "Self-reported" tag, and standings shows the same note in a game's expanded detail. The Discord game-submission notification flags it too.
- **Admin nav visibility**: the "Admin" tab is hidden from the nav bar on every page by default (`public/js/adminNav.js`) and only appears in a given browser tab after logging in at `/admin.html` — it checks for a valid session password in `sessionStorage` and silently reveals the tab if one's found and still valid. There's no way to reach it otherwise; general users only ever see Submit and Standings. A "Log out" button on the admin page clears the stored password and reloads, which removes the tab again — logging back in at `/admin.html` is the only way to get it back.
- **Audit trail**: every change to a game's result is recorded in `game_audit_log` (migration `0005`) via `functions/_gameAudit.js` — the original submission (auto-verified or self-reported), any admin edit, and any admin-triggered WADB recheck, including ones that didn't change anything. Each row captures who did it (`submitter` or `admin`), the before/after winner/draw/status, a note (e.g. why a recheck failed), and the IP address (`CF-Connecting-IP`, via the shared `getClientIp()` in `functions/_util.js`) of whoever performed it — including the original submitter, not just later admin edits, so every game's IP is logged the moment it's uploaded, not only when someone happens to file a report about it. Each game card in the admin panel has a collapsible **History** section (`GET /api/admin/games/:id/history`) showing this trail in plain language; the trail itself is visible to any admin, but the IP on each entry is only ever included in the response for super admins (see below) — a regular admin gets `null` for every entry, submission included, indistinguishable from each other. Deleting a game removes its history along with it (`ON DELETE CASCADE`) — there's nothing left to show a trail against once the game itself is gone.
- **Filtering games by verification source**: the admin panel's Games list has an All / WADB-verified / Self-reported / Manually set filter row (above the Date added/Date played sort toggle), so you can pull up e.g. just the games an admin corrected by hand, or just what WADB verified automatically, without scrolling past everything else. Filters by exact `winnerSource`; unresolved games (no source assigned yet) only show up under "All". The Games section's count badge switches from the usual `(16)` total to `(5/16)` — matching filtered count over the true total — whenever a filter other than All is active, so it's never ambiguous whether "5" is the whole league's game count or just what's currently filtered.
- **Re-check WADB**: each game in the admin panel has a "Re-check WADB" button (`POST /api/admin/games/:id/recheck`) that re-runs `analyzeReplay` against the replay already stored in R2 — no re-upload needed. Useful if a game landed as unresolved because WADB was briefly down, or an admin just wants a second opinion on a manual/self-reported result. If WADB now returns a resolved result it overwrites whatever was there before and is tagged `winner_source = 'wadb'`; if it still can't resolve it, nothing changes but the attempt is still logged. `functions/_wadb.js` holds the shared `callWadb()`/`resolveOutcome()` logic used by both the original submit flow and this recheck endpoint, so a recheck behaves identically to what submission would have done.
- **Two admin tiers**: `ADMIN_PASSWORD` and the optional `SUPER_ADMIN_PASSWORD` both unlock the full admin panel — same access to editing games, rechecking WADB, deleting, merging players, resolving reports. The only difference is IP visibility: `functions/_authAdmin.js` exposes `isSuperAdmin()` alongside `isAdmin()`, and `GET /api/admin/games/:id/history` and `GET /api/admin/reports` both check it before deciding whether to include the real IP in the response at all. A regular admin doesn't get a "hidden" placeholder or any other hint that IP data exists — the field is simply `null` on every entry, submission included, so there's nothing to distinguish "this entry has no IP" from "you're not allowed to see it." This is enforced server-side, not just hidden in the UI — a regular admin can't recover it by inspecting network responses either, and the admin page's HTML never contains IP-related text unless a super-admin session actually fills it in via JS after login. `POST /api/admin/verify` returns `isSuperAdmin` so the page can show a small "Super Admin" badge for that tier only. Leave `SUPER_ADMIN_PASSWORD` unset if you don't want a two-tier setup — everyone who knows `ADMIN_PASSWORD` just never sees IPs, or any indication that they're tracked, anywhere.
- **Two independent prizes**: `functions/api/standings.js` computes both. **Most Wins** is the ladder's actual rank order — total wins, ties broken by win rate, then name; opponent diversity plays no part in it. **Most Active** is a separate, unranked score (`activityScore = gamesPlayed × uniqueOpponents`) that rewards playing a wide spread of people over farming the same one or two opponents — whoever holds the top score gets `isActivityLeader: true`. The two were deliberately decoupled after almost building opponent-diversity into the win ranking itself as a tiebreaker — worth knowing if this behaviour ever looks surprising in a future session's context. Win rate's role has flip-flopped once already in this project's history: it was originally excluded from the Most Wins tiebreak entirely (to stop a 1-game 100% record from outranking a real track record), then deliberately reinstated as the tiebreaker in place of games played — both were considered, this is the current, intentional choice.
- **Marking the current leaders**: both prize leaders get a magenta call-out on the ladder, each scoped to the cell that actually earns them the prize rather than the whole row, so it's clear *why* they're highlighted. Most Wins leader: the Wins cell for whoever's rank 1 (`td.wins-leader` in `public/standings.html`/`style.css`) — rank 1 already *is* that leader by definition given the sort order, the only guard is against highlighting an all-zero-wins board before anyone's actually won a game. Most Active leader: a dedicated **Activity** column showing the literal `gamesPlayed × uniqueOpponents` score (`td.activity-leader`), highlighted once a player holds `isActivityLeader` *and* has played at least `MIN_GAMES_FOR_ACTIVITY_HIGHLIGHT` games (currently 5) — without that floor, a single game against a single opponent trivially produces a "perfect" ratio, which would crown an early/low-volume player over someone with a real track record. This is deliberately its own column rather than reusing the Diversity cell: Diversity (opponents ÷ games) and Activity (opponents × games) can rank players in the opposite order from each other — a player at 73% real volume can legitimately outrank someone else's "perfect" 100% — so highlighting the ratio cell for an activity-based leader was actively misleading (a real issue hit during testing: the highlighted number didn't visually explain the ranking). Diversity stays purely descriptive, no leader logic attached. Most Wins' tiebreak chain (wins → win rate → name) always resolves to exactly one row, so no tie-handling is needed for that highlight. Most Active does need one: exact `activityScore` ties are common enough in a small league (e.g. 20 games × 5 opponents = 10 games × 10 opponents = 100) that `functions/api/standings.js` breaks them by `diversityRatio` (`uniqueOpponents / gamesPlayed`) rather than by games played — games played already gets its weight inside the score itself, so tiebreaking toward it again would quietly turn Most Active into a Most Games prize. A genuine tie on both dimensions still shares the flag.
- **Ladder columns**: Player (with "played 5h ago"-style relative time, from `MAX(played_at, submitted_at)` across a player's games), Wins, a Win % bar (wins ÷ games played, on a plain fixed 0–100% scale — it has a natural ceiling, unlike Diversity below, so it doesn't need relative scaling), Players Faced (unique opponents), Games Played, Diversity (opponents faced ÷ games played, shown as a plain percentage with no bar — a free-for-all can push this over 100%, and an earlier bar version that scaled against the ladder's current max ratio turned out to be more confusing than helpful, since bar length alone doesn't reveal what it's relative to), Activity (the raw `gamesPlayed × uniqueOpponents` score behind the Most Active prize), and Streak.
- **Games log winner highlight**: a game's winner is shown in magenta (`.winner-name`) wherever their name appears — both the collapsed games-log row and the expanded detail. An earlier pass tried a quieter icon-only treatment on the collapsed row (a muted `★`, no colour) to keep the log from reading as a scoreboard, but that was reverted in favour of the more direct magenta highlight everywhere. The expanded detail also dropped its separate per-player W/L badge, since it was just repeating what the winner highlight already shows.
- **Branding**: the site is "Dream League" (tagline "Mini Strategy Roper League") in the header/`<title>` on all three pages (`.brand-text`/`.brand-tagline` in `public/css/style.css`) — matching the Æ mark dreamwa.re itself uses. Internal identifiers (repo folder, D1 database name `wa-mini-league-db`, `package.json`'s `name`) are still the older "wa-mini-league" name; renaming those touches live infrastructure and wasn't done as part of this pass.
- **Timestamp normalization**: D1's `datetime('now')` (used for `submitted_at`, `created_at`, etc.) stores a bare `"YYYY-MM-DD HH:MM:SS"` string — no `T`, no `Z`, no timezone marker. Browsers commonly parse that shape as *local* time rather than UTC, which silently shifted every relative-time display ("Last updated Xh ago", a player's "last played") by the viewer's UTC offset — someone west of UTC would see recent activity reported as further in the past than it actually was. `functions/_util.js`'s `toIsoUtc()` normalizes any such value into an unambiguous ISO string before it's returned from an API endpoint, so the frontend never has to special-case the format; it's applied in `functions/api/games/index.js`, `functions/api/standings.js`, `functions/api/admin/reports/index.js`, and `functions/_gameAudit.js`. `functions/api/standings.js`'s `last_played_at` had a second, related bug: it took `MAX(COALESCE(played_at, submitted_at))` in SQL, but `played_at` (client-supplied, full ISO with milliseconds) and `submitted_at` (D1's bare format) are different string shapes for the same instant, so a plain string `MAX()` across the two wasn't reliably chronological — fixed by comparing `strftime('%s', ...)` (actual parsed UTC seconds) instead of the raw strings.
- **Scheme & map downloads**: `public/index.html` has a "Scheme & Maps" section below the drop zone linking to `public/downloads/strategy-roper.wsc` (the league's scheme) and `public/downloads/sroper-map-pack.zip` (10 custom maps). These are static files served straight from Pages — no API involved, no admin control over them yet. `public/downloads/sroper-maps.zip` is a leftover first copy of the map pack (contains macOS resource-fork clutter, `__MACOSX/`) that isn't linked from anywhere; safe to delete whenever someone approves it.
- **The SRoper explainer (`/scheme.html`)**: the pitch, the 3 rule changes (continuous one-at-a-time crate spawns, crate HP bonus 20→10, optional turn-1 bazooka), map recommendations, 5 strategy tips, and a video walkthrough — rewritten into the site's own voice from the league organiser's original announcement, not reproduced verbatim. Linked from the homepage's Scheme & Maps card ("What is SRoper, and how do I play it?"), not from the main nav — it's a reference page, not one of the three task flows. The video is served from a **second, separate R2 bucket** (`wa-mini-league-media`, binding `MEDIA`) rather than as a static Pages asset: at ~200MB it's well over [Cloudflare Pages' 25MB-per-file limit](https://developers.cloudflare.com/workers/platform/limits/), which the small scheme/map-pack downloads never hit. `functions/api/media/[key].js` streams it back (public, no admin password needed — it's promotional content, not gameplay evidence) and explicitly handles HTTP Range requests (`env.MEDIA.get(key, { range: request.headers })`, responding `206` with a matching `Content-Range` when one's present) so the `<video>` player on the page can seek/scrub instead of buffering the whole file first. See the setup section for how to create the bucket and upload the video — that step has to be run from your own machine (Cloudflare credentials aren't available in this environment).

## Setup

1. Install deps:
   ```
   npm install
   ```

2. Create the D1 database and note the returned `database_id`:
   ```
   npx wrangler d1 create wa-mini-league-db
   ```
   Paste that ID into `wrangler.toml` under `[[d1_databases]]`.

3. Create the R2 bucket for replay storage:
   ```
   npx wrangler r2 bucket create wa-mini-league-replays
   ```

4. Create the R2 bucket for public site media, then upload the scheme's video walkthrough into it (run this from wherever the video file actually lives on your machine — it's too large for this environment to upload on your behalf):
   ```
   npx wrangler r2 bucket create wa-mini-league-media
   npx wrangler r2 object put wa-mini-league-media/media/sroper-showcase.mp4 --file="/path/to/Sroper Showcase.mp4" --content-type=video/mp4 --remote
   ```
   The key (`media/sroper-showcase.mp4`) has to match what `/scheme.html` requests (`/api/media/sroper-showcase.mp4`) — if you ever swap in a different video, either reuse this same key or update both the filename in `functions/api/media/[key].js`'s callers and the `<source>` URL in `public/scheme.html`.

5. Run the schema migration:
   ```
   npm run db:migrate:remote
   ```
   (use `db:migrate:local` first if you want to test with `wrangler pages dev` locally)

6. Set the admin password as a secret (never commit this):
   ```
   npx wrangler pages secret put ADMIN_PASSWORD
   ```

   (Optional) Set a separate super-admin password too — both log in to the same admin panel, but only the super-admin one reveals IP addresses (see below):
   ```
   npx wrangler pages secret put SUPER_ADMIN_PASSWORD
   ```

7. (Optional) Discord notifications — needs a real Discord *server* (incoming webhooks can't post to a group DM). In your server:
   - Create two channels (e.g. `#game-log` and `#reports`), each with its own webhook: channel settings (or Server Settings → Integrations → Webhooks) → New Webhook → Copy Webhook URL.
   - If you want issue reports to @-mention a role, enable Developer Mode (User Settings → Advanced) so you can right-click the role and Copy ID.
   - Set whichever of these you want as secrets — any left unset just means that notification type is silently skipped:
     ```
     npx wrangler pages secret put DISCORD_GAMES_WEBHOOK_URL
     npx wrangler pages secret put DISCORD_REPORTS_WEBHOOK_URL
     npx wrangler pages secret put DISCORD_ADMIN_ROLE_ID
     ```
   - To switch servers/channels later, just overwrite the secret with a new webhook URL (or role ID) — no code changes needed.

8. Deploy:
   ```
   npm run deploy
   ```
   Or connect the repo to Cloudflare Pages in the dashboard for git-based auto-deploys, same as your other Cloudflare-hosted sites.

## Local dev

```
npm run dev
```
Runs `wrangler pages dev` with local D1 + R2 bindings (make sure you ran `db:migrate:local` first).

## Notes / things to revisit later

- Admin auth is a single shared password checked per-request — fine for a small trusted league, but if this grows, swap for per-moderator accounts.
- No rate limiting or spam protection on `/api/submit` — running on the honour system by design for now.
- The fuzzy player-matching is a suggestion only; it's not perfect and doesn't need to be, since a human always confirms it before submit.
- Winner detection depends on `wormsarmageddon.com` staying up and `analyzeReplay` staying public. It's a hard dependency at submit time, but a soft one for data integrity — a WADB outage (or the endpoint changing/requiring auth again) just means new games land as `unresolved` until an admin sets the winner by hand, nothing breaks or gets blocked. It's also literally one guy's machine running the actual game engine, not a monitored service, so treat it as a nice-to-have rather than something to build hard guarantees on top of.
- Already run some but not all of these migrations on a live database? Only run the ones you're missing directly, not the whole chained script — `0002`, and now `0004`, are both plain `ALTER TABLE ADD COLUMN`, which errors if run twice:
  ```
  npx wrangler d1 execute wa-mini-league-db --remote --file=migrations/0004_outcome_note.sql
  ```
  (`0001`, `0003`, and `0005` are safe to re-run — `CREATE TABLE IF NOT EXISTS` — `0002` and `0004` aren't.)
- Reports don't do anything with the captured IP beyond the rate limit and showing it to admins for context — there's no blocklist, ban list, or de-anonymisation feature. If abuse becomes a real problem beyond the 5-per-hour cap, that's the next thing to add.
